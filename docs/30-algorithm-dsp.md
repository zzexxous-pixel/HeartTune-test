# 30 · 신호처리 알고리즘 설계 및 검증

> 손가락 PPG에서 심박수(BPM)와 리듬(부정맥)을 추출하는 파이프라인.
> 구현: `src/dsp.js` · 검증: `tests/dsp.test.js` (`npm run test:unit`)
> 최종 검증: **2026-10-24 — 18개 테스트 전부 통과** (`node --test`, Node 22)
> (2026-10-19 이전 문서에 적힌 "20개 테스트 통과"는 적응형 캘리브레이션 도입 이전 기록으로, 실제 파일과 불일치였음)

## 1. 파이프라인

```
카메라 프레임 (rVFC / rAF 폴백)
      │  64×64 축소 → 중앙 ROI 채널 평균(R 우세 시 R, 그 외 G)
      ▼
원시 시계열 (가변 fps)  ──재표본화──▶  균일 15 Hz
      ▼
대역통과 0.7~4.0 Hz (4차 Butterworth, forward-backward)
      ├──▶ FFT(슬라이딩 윈도, 한닝 창, 부포물선 보간)
      ├──▶ 자기상관
      ├──▶ 박동 검출(아래 2절) ──▶ IBI 변동성(CV, RMSSD) ──▶ 리듬 판정
      └──▶ 세 추정치 합의/중재 (아래 2-1) ──▶ 최종 BPM ──▶ 필터 대역 트래킹
```

> **카메라 워밍업 (2026-10-24)**: 측정 시작 후 3초(`CAMERA_SIGNAL_WARMUP_SEC`, main.js)는
> 자동노출/손가락 접촉 안정화 구간으로 신호값이 5→255(포화)까지 요동해 가짜 박동을 만든다.
> 이 구간은 기록·분석에서 제외한다(경고 표시·타이머·진행 링은 정상 동작).
## 2. 박동 검출기 설계

1. **양극 포락선**: `max(signal, 0)` — 음의 골짜기는 0으로 클램프
2. 짧은 이동평균 평활 (≥3샘플)
3. **임계값 = 상위 피크(90백분위)의 35%**
4. **돌출도 기반 탐욕 선택**: 큰 피크부터 선점, `minGap = 0.28~0.32초` 불응기

### 구현 중 실제로 발생했던 버그 3건 (모두 테스트로 회귀 방지)

| # | 버그 | 증상 | 원인 | 수정 |
|---|---|---|---|---|
| 1 | DC 제거 누락 | 필터 출력 `-9~53` 비대칭 | PPG의 DC(0~255 레벨)를 highpass에 그대로 투입 → 수 초간 천이(transient) | 필터 전 평균 제거 |
| 2 | 제곱/절대값 포락선 | 박동 수가 2배 | ① `signal²`: 음의 골짜기(4.9)가 양의 피크(4.3)보다 커짐 ② `\|signal\|`: 골짜기가 박동으로 검출 | **양극** 포락선 사용 |
| 3 | 중앙값 기반 임계값 | 중첩파(dicrotic) 통과 → 2배 검출 | 피크 대부분이 수축기라 중앙값이 낮게 잡힘 | 상위 피크(90백분위)의 35% 기준 |

### 테스트 신호 설계에서 발견한 오류

샘플 루프 안에서 매번 IBI를 새로 뽑는 방식은 위상 누적 때문에 지터가 **평균화**되어 실제 박동 간격이 변하지 않는다(실측 cv 0.09). 박동 간격을 **박동 단위로 확정**한 뒤 샘플을 채우는 방식으로 수정.

### 2-1. 하모닉(중첩파) 혼동 해소 — `resolveBpmEstimate()` (2026-10-19 신규)

**증상**: 45 BPM 신호가 70 BPM, 55 BPM 신호가 93 BPM, 노이즈가 큰 72 BPM 신호가 139 BPM으로 측정됨.

**원인 (연쇄 오류)**
1. 손가락 PPG는 수축기 피크 + 중첩파(dicrotic wave) 때문에 스펙트럼에 **2차 하모닉이 강하게** 나타난다.
2. 저박동에서는 2차 하모닉 크기가 기본파보다 커져, FFT 최대 피크만 쓰면 **2배 주파수**를 고른다.
   - 실측: 45 BPM → FFT 89.65 Hz-bin(89.65 BPM), 55 BPM → FFT 109.58
3. 그 값이 **필터 트래킹 중심**이 되면서 대역이 0.93~3.21 Hz 로 잘못 좁혀진다(기본파 0.75 Hz 차단).
4. 좁아진 대역에서 박동 검출기가 중첩파/하모닉을 박동으로 세어 **박동 수 2배** → CV 폭증 → "리듬 불규칙" 오판.

**해결** — 세 추정치를 동시에 보고 합의를 우선한다.

| 조건 | 채택 |
|---|---|
| 10초 미만 초기 구간 | 자기상관 ≈ IBI 중앙값이면 두 값의 평균 (5초 고속 포착 유지) |
| FFT ≈ 자기상관 (12% 이내) | 두 주파수 추정치의 합의를 신뢰 |
| 불일치 | **IBI 중앙값(시간영역)이 중재** — 0.30초 불응기 덕분에 중첩파를 박동으로 세지 않아 하모닉에 강함 |
| 박동 수 부족 | 주파수 추정치 중 기저 심박수(prior)에 가까운 값 |

현재 코드의 tracking 진입 조건은 45~195 BPM이다. 40 BPM 지원 확대는 광대역·FFT 탐색·초기 합의 조건까지 함께 검토할 별도 결정이며, 아직 변경하지 않았다.
`filterState`/`estimator` 필드에 어느 추정치가 채택되었는지(`source`, `agreement`, `harmonicCorrected`)가 남는다.

### 2-2. 리듬 판정 이중 정제 — 실측 오탐 사례 대응 (2026-10-24 신규)

**증상(사용자 실측 CSV 2건, 30초)**: 화면 파형은 안정적으로 보였는데 결과가 "부정맥".
**원인**: 첫 ~3초 안정화 요동의 가짜 피크가 박동으로 검출되어 IBI가 394~503ms로 뒤틀리고
CV가 0.16~0.23로 폭증(안정화 구간 제외 시 CV 0.046~0.059의 규칙 리듬). 화면 파형은
최근 90샘플만 그려 안정적으로 보였을 뿐 분석은 전체 버퍼를 쓴 것이 디버깅 포인트였다.

**해결 — `evaluateRhythm()` IBI 2차 정제(MAD)**

| 단계 | 규칙 | 목적 |
|---|---|---|
| 1차 | 중앙값의 [0.45, 1.85] 배 범위 밖 제거 | 극단값(놓친 박동의 2배 IBI 등) |
| 2차 | 중앙값 ± max(3.5×MAD, 40ms) 밖 제거 | 이중 검출·가짜 피크의 '튀는' IBI |

- 문턱이 실제 변동 폭에 **비례**하므로, 연속적으로 넓게 변하는 불규칙 리듬(부정맥)은
  정제되지 않고 그대로 irregular 로 판정된다(테스트 18번으로 보존 검증).
- 워밍업 제외(main.js)와 함께 2층 방어: 초반 요동은 애초에 기록하지 않고,
  측정 중간 아티팩트는 정제로 막는다.
- 검증: 해당 실측 CSV 2건 모두 정상 판정으로 교정(BPM 78/77 유지, CV 0.050/0.059).

## 4. 잠정 임계값 (⚠️ 임상 검증 필요)

- 부정맥 의심: **CV > 0.14** (규칙 0.04 vs 불규칙 0.22 사이) — CV 계산 전 IBI 이중 정제(2-2절) 적외
- 신뢰 가능 판단: 박동 수 ≥ max(8, 기대치 40%)
- 15초 측정은 리듬 판정을 "참고"로 강등

> 카메라 PPG는 모션 아티팩트에 민감해 흔들림과 부정맥을 구분하지 못할 수 있음.
> 화면 문구는 "리듬이 고르지 않아요. 의사와 상담해 보세요" 수준으로 한정.
